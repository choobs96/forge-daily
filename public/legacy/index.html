Module 1 · Foundations Beginner→Adv

Advanced SQL

From "answers a question" to "production-quality, performant, deterministic."

SQL is 70% of the AE job. You probably already write it daily — but there's a gap between "works for this report" and "works in a 100M-row Spark cluster with 12 downstream models depending on it."

1. CTEs vs Subqueries — the Style You'll Be Judged On

Every dbt model you'll touch uses CTEs. Subqueries are read once, top-to-bottom; nested subqueries are unreadable.

-- 🟢 AE style
with active_jobs as (
  select job_id, account_id, created_at
  from {{ ref('stg_jobs') }}
  where __is_deleted = false
),
job_counts as (
  select account_id, count(*) as job_count
  from active_jobs
  group by account_id
)
select * from job_counts where job_count > 5;
Production gotcha
Always filter __is_deleted = false on Kafka CDC tables (jobs, accounts, sites, contacts, etc.). Missing it = production correctness bug.

2. Window Functions — the AE Power Tool

Window functions let you do row-level + aggregate together. They're how every "first/last", "running total", "rank", "lag/lead" question gets solved.

The anatomy

function() over (
  partition by <reset group>
  order by <ordering within group>
  rows between <frame>
)

The seven you must know cold

FunctionUse Case
row_number()Dedupe — keep latest row per key
rank() / dense_rank()Leaderboards, ties handling
lag() / lead()Period-over-period, "previous status"
sum() overRunning total / cumulative
first_value() / last_value()First/last status, signup channel
ntile(n)Quartile, decile buckets
count(*) over (partition by)"How many siblings does this row have"

The classic dedupe pattern (memorise this)

with ranked as (
  select *,
    row_number() over (
      partition by account_id
      order by updated_at desc
    ) as rn
  from raw.accounts
)
select * from ranked where rn = 1;

3. Joins — beyond INNER/LEFT

SEMI JOIN int

"Rows in A that have a match in B" — no row multiplication, no columns from B.

select * from jobs j
where exists (
  select 1 from bookings b
  where b.job_id = j.id
);

ANTI JOIN int

"Rows in A with no match in B." Use NOT EXISTS over NOT IN (NULL-safe).

select * from accounts a
where not exists (
  select 1 from jobs j
  where j.account_id = a.id
);

Cross / Cartesian adv

Multiplies every row of A by every row of B. Useful for date spines, cohort grids — dangerous otherwise.

Lateral / Cross Apply adv

Per-row subquery that can reference outer columns. In Spark: LATERAL VIEW for exploding arrays.

4. Join Fan-Out — the silent killer

If orders has 100 rows and order_items has 500 rows, joining them produces 500 rows. SUM(order_value) is now 5× the truth.

-- ❌ wrong: order_value is duplicated per item
select sum(o.order_value)
from orders o
join order_items i on i.order_id = o.id;

-- ✅ correct: aggregate one side before joining
with items_per_order as (
  select order_id, count(*) as item_count
  from order_items group by order_id
)
select sum(o.order_value), sum(i.item_count)
from orders o
left join items_per_order i on i.order_id = o.id;
Always test grain after a join
Run count(*) vs count(distinct pk) after every join. If they differ, you have fan-out.

5. NULL Handling — the trap

  • NULL = NULL is NULL, not true. Use IS NULL.
  • NOT IN (subquery) returns zero rows if the subquery has any NULL. Use NOT EXISTS.
  • COUNT(*) counts NULLs; COUNT(col) ignores them.
  • SUM(NULL + 1) = NULL — wrap in COALESCE.

6. Pivots & Unpivots

-- pivot via conditional aggregation
select
  account_id,
  sum(case when status = 'won' then 1 else 0 end) as wins,
  sum(case when status = 'lost' then 1 else 0 end) as losses
from deals
group by account_id;

7. Query Plans — read them, don't fear them

In Databricks: EXPLAIN FORMATTED <query>. Top → bottom = inside → outside.

  • Scan — reading a table. Watch PartitionFilters.
  • BroadcastHashJoin — small table broadcast to all nodes. Fast.
  • SortMergeJoin — both sides large; shuffled. Slow but unavoidable.
  • Exchange (Shuffle) — repartitioning. Expensive — minimise.
  • Filter — predicate push-down should put it as close to Scan as possible.

SQL Performance Cheat Sheet

# Predicates push down — filter EARLY WHERE date >= '2026-01-01' → before any JOIN # Project only what you need SELECT id, name → not SELECT * # Aggregate before joining (avoid fan-out) # Use EXISTS over IN for nullable subqueries # Avoid functions on join keys (kills partition pruning) ON a.id = b.id ✅ ON UPPER(a.id) = b.id ❌ # Broadcast small dim tables explicitly when planner misses SELECT /*+ BROADCAST(dim) */ ...

Pandas → PySpark — what changes

PySpark is pandas-adjacent but lazy (no execution until .show() / .collect()) and distributed. Key differences:

# pandas
df.groupby('account_id')['value'].sum()

# PySpark
from pyspark.sql import functions as F
df.groupBy('account_id').agg(F.sum('value'))

# PySpark filter
df.filter(F.col('date') >= '2026-01-01')

import click

@click.option('--run-date', default=str(date.today()))

Pattern: API ingestion with retries

import requests

@retry(wait=wait_exponential(multiplier=1, max=30), stop=stop_after_attempt(5))

Git, GitHub & CI/CD

The single biggest "looking like an engineer" lever.

Analysts often live in notebooks or Tableau workbooks — no version control. AEs live in Git. The mental model: every change is a branch → PR → review → merge.

The Git Mental Model

ConceptWhat it is
RepositoryA folder + complete history of every change
BranchAn independent line of work. main = production. Feature branches off main.
CommitA snapshot + message. Atomic — one logical change.
PushUpload your branch to GitHub.
Pull Request"Please review and merge my branch."
MergeIntegrate one branch into another.
RebaseReplay your commits on top of latest main. Cleaner history than merge.

The Daily Loop

# start a new feature
git checkout main
git pull origin main
git checkout -b feat/DAE-422-stg-accounts

# work, then save it
git add models/staging/stg_accounts.sql
git commit -m "feat: [DAE-422] Add staging model for accounts"

# push and open a PR
git push -u origin feat/DAE-422-stg-accounts
gh pr create --title "feat: [DAE-422] stg_accounts" --body "..."

# after review, merge via GitHub UI (squash merge)

Commit Hygiene

  • One logical change per commit. "Add stg_accounts" not "stg_accounts and some other fix and docs."
  • Conventional Commits: feat: …, fix: …, chore: …, refactor: …, docs: …
  • Imperative mood: "Add", "Fix", "Refactor" — not "Added", "Fixing".
  • Reference ticket: feat: [DAE-422] Add staging model

Resolving Merge Conflicts

# your branch is behind main — rebase to bring it up
git fetch origin main
git rebase origin/main

# conflict in a file — open it, look for <<<<<<< markers
# fix it, then:
git add <file>
git rebase --continue

# abort if it's a mess
git rebase --abort
Never force-push to main
git push --force on main rewrites everyone's history. Use it only on your own feature branches, and prefer --force-with-lease.

CI/CD for Data Projects

CI = Continuous Integration. Every PR triggers automated checks: lint, compile, test, run dbt on a sample.

For a dbt project, a typical PR pipeline:

  1. Lint — sqlfluff checks SQL style
  2. Compile — dbt compile catches syntax errors
  3. Build modified — dbt build --select state:modified+ runs only changed models
  4. Test — schema + data tests run automatically as part of build
  5. Slim CI — only re-run what actually changed since main

Module 4 · Core Intermediate

Data Modeling

The hardest, highest-leverage skill. This is where AE earns its title.

Modeling = deciding the shape of your tables: what's a fact, what's a dimension, what's the grain, how do they relate. Get this wrong and every dashboard is wrong forever.

Normalization (3NF) vs Dimensional

3NF / NormalizedDimensional (Kimball)
Where usedOLTP — transactional databasesOLAP — warehouses
GoalNo duplication, fast writesFast reads, intuitive queries
ShapeMany tables, lots of joinsStar schema — fact + dims
Exampleproduction MySQL DBsyour dbt marts/ layer

Kimball Star Schema — the AE bread & butter

A fact is something that happened (a transaction, an event). A dimension describes the actors (who, what, where, when).

Fact table

  • One row = one event (1 booking, 1 job posted)
  • Mostly foreign keys + numerical measures
  • Grain stated explicitly (e.g. "one row per job posted")
  • Examples: fct_jobs, fct_bookings, fct_payments

Dimension table

  • One row = one entity (1 account, 1 contractor, 1 product)
  • Mostly descriptive attributes
  • Slowly changes over time (SCDs)
  • Examples: dim_accounts, dim_contractors, dim_dates

The Grain — what one row represents

Always declare it. Write it in the model docs. Every join, every aggregate either preserves or changes the grain. Confusion about grain = duplicated rows = wrong metrics.

-- fct_job_assignments grain: one row per (job_id, contractor_id)
-- fct_jobs            grain: one row per job_id
-- fct_daily_revenue   grain: one row per (account_id, date_day)

Slowly Changing Dimensions (SCDs)

TypeBehaviorUse case
Type 0Never changeBirth date
Type 1Overwrite — only current valueCustomer email (don't care about history)
Type 2Keep history with valid_from / valid_to / is_currentPlan tier, sales rep — most common in AE
Type 3Add column for "previous value"Rare; limited history
Type 4Separate history tableHeavy-history dims
Type 61+2+3 hybridEdge cases

SCD Type 2 in dbt — snapshots

-- snapshots/accounts_snapshot.sql
{% snapshot accounts_snapshot %}
{{ config(
    target_schema='snapshots',
    unique_key='account_id',
    strategy='timestamp',
    updated_at='updated_at'
) }}
select * from {{ source('raw', 'accounts') }}
{% endsnapshot %}

This builds a table with dbt_valid_from and dbt_valid_to columns — every change to updated_at creates a new row.

Surrogate vs Natural Keys

  • Natural key — comes from source: email, job_number. Can change.
  • Surrogate key — generated, immutable: account_sk = md5(account_id || updated_at).
  • For SCD2 dims: surrogate key must include the time component, otherwise joins break.
  • dbt: {{ dbt_utils.generate_surrogate_key(['col_a','col_b']) }}
Production gotcha
generate_surrogate_key with a nullable column gives identical hashes for different NULL rows. Always use a column that's unique-per-row.

The Three-Layer Pattern (a common dbt convention)

LayerPurposeExamples
staging/Light cleaning + rename. 1:1 with source.stg_accounts, stg_jobs
intermediate/Business logic, joins, fan-out resolution.int_account_jobs_joined
marts/Final fact/dim tables exposed to BI.fct_jobs, dim_accounts

Medallion Architecture (Databricks/Lakehouse term)

Same idea, different naming:

  • Bronze — raw ingested data, minimal transformation. Mirrors source.
  • Silver — cleaned, conformed, joined. Roughly = staging + intermediate.
  • Gold — business-ready aggregates. Roughly = marts.

Modeling Anti-Patterns

The "one big table"

Dumping every column from every source into fct_everything. Looks easy, becomes unmaintainable. Resist.

Mixing grains

Joining fct_jobs (one row per job) to fct_job_events (many per job) without aggregating first. Fan-out everywhere.

Wide skinny dim

Dimension with 200 columns, 90% nulls. Split into role-playing or junk dimensions.

Forgetting the date dim

Always have dim_dates. Lets you reason about fiscal weeks, holidays, business days — without case statements.

What's the grain of a fact table and why does it matter?
Grain = what one row represents (e.g. "one row per job per day"). It's the contract for the table — every metric is implicitly per-grain. Mixing grains in joins causes silent fan-out and wrong sums.
Click
When do you use SCD Type 2 vs Type 1?
Type 2 when historical accuracy matters (was this account on "Pro" plan when this lead was sold?). Type 1 when you only ever need the current value (their current email address).
Click

Star: dims are denormalized — fewer joins, easier for BI. Snowflake: dims are normalized into sub-dims (e.g. product → category → department) — more joins, less redundancy. Star wins in most modern warehouses.

Module 5 · Core Intermediate

Data Warehousing Concepts

Why your query is slow — and how to make it 100× faster.

Modern warehouses (Databricks, Snowflake, BigQuery) are columnar, distributed, and lazy. Knowing what they actually do under the hood is the difference between a 5-second query and a 5-minute one — at the same cost.

OLTP vs OLAP

OLTP (transactional)OLAP (analytical)
Exampleproduction MySQLDatabricks, Snowflake, BigQuery
WorkloadMany tiny writes/readsFew large scans / aggregations
StorageRow-orientedColumn-oriented
Optimised forLatency on single rowThroughput on millions of rows

Columnar storage — the OLAP secret

Row-store writes a row's fields together: [id1, name1, age1] [id2, name2, age2] …

Column-store writes each column together: [id1, id2, …] [name1, name2, …] [age1, age2, …]

Implication: SELECT AVG(age) reads ONLY the age column. SELECT * reads everything. This is why SELECT * is expensive in OLAP and basically free in OLTP.

File formats

FormatTypeUse case
CSVRow, textInterchange, never analytical storage
JSONRow, nestedAPI responses, semi-structured raw
ParquetColumnar, compressedThe standard for warehouse storage
ORCColumnar, compressedHive ecosystem
AvroRow, schema'dStreaming (Kafka payloads)
Delta / Iceberg / HudiParquet + transaction logLakehouse table formats — ACID on object storage

Delta Lake — the lakehouse table format

Delta = Parquet files + a _delta_log/ JSON transaction log. The log records every commit (add files, remove files, schema change). This gives you:

  • ACID transactions on cheap object storage (S3/ADLS/GCS).
  • Time travel: SELECT * FROM t VERSION AS OF 12
  • Schema enforcement & evolution
  • MERGE INTO — upserts (the CDC backbone)
  • OPTIMIZE + ZORDER — small-file compaction + clustering

Partitioning

Physically splits a table by a column value. Queries that filter on that column skip entire partitions.

-- partitioned by date_day → query only scans 1 day
create table events (
  event_id bigint,
  user_id bigint,
  date_day date,
  ...
)
using delta
partitioned by (date_day);
Don't over-partition
Partition cardinality should be moderate (10s–1000s). Partitioning by user_id with 10M users = 10M tiny files = disaster.

Clustering / Z-Ordering

Within a partition (or whole table), sort the physical files by a column so scans can skip files via min/max stats.

optimize events zorder by (user_id);

Use Z-order on high-cardinality columns frequently filtered on. Liquid Clustering (newer) replaces Z-order — pick this on new Delta tables.

The 4 Performance Levers

1. Partition pruning

Filter on partition column. Skip whole folders.

2. Predicate pushdown

Filter before any join. Engine reads less Parquet.

3. Column projection

SELECT only what you need. Columnar storage rewards this.

4. Broadcast joins

Small dim broadcast to all workers — no shuffle. /*+ BROADCAST(dim) */

Compute Models

DescriptionExamples
Storage = ComputeTied — bigger table needs bigger boxOld Postgres data warehouses
Storage ≠ ComputeDecoupled — scale them independentlyDatabricks, Snowflake, BigQuery
ServerlessAuto-scale, pay per queryDatabricks SQL Serverless, BigQuery

Costs — the new AE concern

  • You're billed for compute time, not data volume scanned (mostly). Bigger warehouse = faster but more $/sec.
  • Rule of thumb: small warehouse for dev/sandbox; right-size production by p95 query latency.
  • Common waste: SELECT * in dashboards, queries running 24/7 on a giant warehouse, no auto-stop.

Flashcards

Click
Why is SELECT * bad in OLAP but fine in OLTP?
Columnar storage reads only requested columns. SELECT * forces every column off disk — often 10–50× more I/O than needed. OLTP is row-oriented so it costs the same regardless.
Click
What does OPTIMIZE … ZORDER BY (col) do?
Compacts small Parquet files into bigger ones AND sorts data by col so engines can skip files via min/max stats during filtered queries. Speeds up filters on high-cardinality columns.
Click
Why does Delta Lake give you ACID on S3/cloud storage?
A transaction log (_delta_log/) ordered as a sequence of JSON commits. Atomic file rename guarantees serializability. Without it, S3 is "eventually consistent" and you can't do upserts safely.

Recap

  • Parquet is the standard format; Delta/Iceberg add ACID + time travel on top.

Module 6 · Core Int→Adv

dbt Mastery

The framework that defined Analytics Engineering.

dbt is the tool, but more importantly, it's the workflow. SELECT statements → version-controlled, tested, documented, lineage-aware models. If you can ship dbt comfortably, you can call yourself an AE.

The dbt Mental Model

  1. You write SELECT statements in .sql files inside models/.
  2. dbt wraps each one in CREATE TABLE AS or CREATE VIEW AS.
  3. You reference other models with {{ ref('model_name') }} — dbt builds the DAG.
  4. dbt run executes them in dependency order.
  5. dbt test runs assertions you've declared.
  6. dbt build = run + test together.

Project Anatomy

my_dbt_project/
├── dbt_project.yml         # project config
├── profiles.yml             # warehouse connection
├── models/
│   ├── staging/
│   │   ├── _sources.yml     # declare raw tables

Incremental Models — the most-asked AE topic

-- models/marts/fct_events.sql
{{ config(
    materialized='incremental',
    unique_key='event_id',
    on_schema_change='sync_all_columns',
    incremental_strategy='merge'
) }}

select *
from {{ ref('stg_events') }}
{% if is_incremental() %}
  where updated_at > (select max(updated_at) from {{ this }})
{% endif %}

On first run, no filter → full build. After that, only new rows. unique_key + merge strategy updates existing rows where the key matches.

Incremental gotchas
  • Late-arriving data: filter on updated_at > max - 1 hour for safety margin.
  • Schema changes: set on_schema_change or you'll get errors.
  • Always rebuildable: dbt run --full-refresh drops and rebuilds.
  • In a CDC pipeline: first run after adding a CDC checkpoint column may need --full-refresh.

Databricks & Spark

The platform you're already using — but probably under-using.

Spark is the engine; Databricks is the managed product around it. As an AE, knowing how Spark thinks about your query is a force multiplier — you'll diagnose 10x slowdowns yourself instead of escalating.

Spark Architecture (one-paragraph version)

A Driver coordinates. Multiple Executors on worker nodes run tasks in parallel. Data is partitioned across executors. The driver builds a DAG of stages from your code, then schedules tasks. Shuffles (data movement between executors) are the expensive operation.

The Spark Vocabulary

TermMeaning
TransformationLazy op (filter, groupBy, join). Builds plan, doesn't execute.
ActionTriggers execution (show, collect, count, write).
PartitionA chunk of data on one executor.
StageA group of tasks that can run without a shuffle in between.
ShuffleRepartitioning data across nodes — expensive.
JobOne action = one job.
AQEAdaptive Query Execution — runtime re-optimisation.
PhotonDatabricks' vectorised native execution engine. Free speed.

Join Strategies

Broadcast Hash Join

Small side broadcast to all executors. No shuffle. Fastest.
Triggers if smaller side < autoBroadcastJoinThreshold (default 10MB).

Sort-Merge Join

Both sides shuffled by key, sorted, merged. Default for big-vs-big.

Shuffle Hash Join

Less common; both shuffled, hash table built on smaller.

BNLJ (Cartesian)

Broadcast nested loop. The "you broke something" join — usually a missing join key.

Reading a Spark UI / Query Profile

  1. Jobs tab — find the slow job, click in.
  2. Stages tab — look for a stage with high duration or high shuffle read/write.
  3. Tasks — check for skew: one task taking 10× the rest = skewed partition key.
  4. SQL/DataFrame tab — see the physical plan. Look for SortMergeJoin where you expected BroadcastHashJoin → missing broadcast hint or stale stats.

Common Spark Performance Issues

SymptomLikely causeFix
One task takes 10× longer than othersData skew (one key has 90% of rows)Salting, AQE skew handling, broadcast if other side is small
Many tiny output filesToo many partitions → too many writerscoalesce(n) or OPTIMIZE after
Job takes ages on small dataCluster spin-up overheadUse serverless or warm cluster pool
SortMergeJoin where BHJ expectedStats stale or table too bigANALYZE TABLE; explicit /*+ BROADCAST(t) */
Driver OOM.collect() on huge DataFrameNever collect big data to driver

PySpark Patterns You'll Actually Use

from pyspark.sql import functions as F, Window

# Read Delta
df = spark.read.format("delta").table("main.silver.jobs")

# Filter + project (predicate pushdown happens automatically)
df = df.filter(F.col("is_deleted") == False) \
       .select("job_id", "account_id", "created_at")

# Dedupe latest per key
w = Window.partitionBy("job_id").orderBy(F.col("updated_at").desc())
df = df.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")

# Join with explicit broadcast
dims = spark.read.table("main.silver.dim_accounts")
joined = df.join(F.broadcast(dims), "account_id", "left")

# Write to Delta with merge (upsert)
from delta.tables import DeltaTable
tgt = DeltaTable.forName(spark, "main.gold.fct_jobs")
tgt.alias("t").merge(
    df.alias("s"), "t.job_id = s.job_id"
).whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()

-- liquid clustering (newer, preferred for new tables)
alter table fct_jobs cluster by (account_id, event_date);

Flashcards

Click
Why is a broadcast hash join faster than a sort-merge join?
No shuffle. The small side is sent to every executor once; each executor joins locally. Sort-merge shuffles both sides across the network and sorts them — expensive.
Click
You see one task in a stage taking 20× longer than the others. What's likely?
Data skew — one key in the join/groupBy has dramatically more rows. Fix: AQE skew handling, salting, or broadcast the smaller side.
Click
What does VACUUM on a Delta table do? When NOT to run it?
Removes data files older than the retention period (default 7 days) that are no longer referenced. Don't run with a short retention if you rely on time travel — you'll lose history.
Spark Check
Your join takes 12 minutes. EXPLAIN shows SortMergeJoin. The dim table is only 5 MB. What's the fix?
Recap
  • Driver schedules, executors run, shuffles cost. Photon = free speedup.
  • Transformations lazy, actions trigger. Skew = the #1 hidden killer.
  • Broadcast small dims, sort-merge big-vs-big.
  • Delta needs OPTIMIZE/VACUUM; time travel is a debugging superpower.
  • Unity Catalog = 3-level namespace + RBAC + lineage.

Orchestration

DAGs, schedules, retries, SLAs — making "run every morning" reliable.

An orchestrator schedules and runs your pipeline, handling retries, alerts, and dependency order. Whether it's Airflow, Dagster, Prefect, or Databricks Workflows — the concepts are the same.

The Universal Concepts

ConceptWhat it is
DAGDirected Acyclic Graph — tasks + dependencies
Task / OperatorOne unit of work (run SQL, call API, run dbt)
ScheduleWhen DAG runs (cron or interval)
Execution DateThe logical date the run represents (often "yesterday")
RetriesAuto-retry failed tasks N times with backoff
SLAMax acceptable duration; breach = alert
BackfillRe-run for historical dates
IdempotencySame input → same output, every time

Airflow Mental Model

# dags/daily_revenue.py
from airflow import DAG
from airflow.providers.databricks.operators.databricks import DatabricksRunNowOperator
from datetime import datetime, timedelta

default_args = {
    'owner': 'data-team',
    'retries': 2,
    'retry_delay': timedelta(minutes=10),
    'sla': timedelta(hours=2),
}

with DAG(
    dag_id='daily_revenue',
    default_args=default_args,
    schedule='0 6 * * *',  # every day 6am
    start_date=datetime(2026, 1, 1),
    catchup=False,
    tags=['finance', 'daily'],
) as dag:

    ingest = DatabricksRunNowOperator(
        task_id='ingest_salesforce',
        job_id=123,
    )
    transform = DatabricksRunNowOperator(
        task_id='dbt_build',
        job_id=456,
    )
    publish = DatabricksRunNowOperator(
        task_id='publish_dashboard',
        job_id=789,
    )

    ingest >> transform >> publish  # dependency order

Idempotency — the non-negotiable property

If your job runs twice for the same date, it should produce the same result. Otherwise retries and backfills corrupt your data.

  • Bad: INSERT INTO fact_x VALUES ... — duplicates on retry.
  • Good: MERGE INTO fact_x USING ... ON id = id — upserts cleanly.
  • Better: DELETE FROM fact_x WHERE date = '{{ ds }}'; INSERT ... — "rebuild this date's slice."
  • Best: dbt incremental with unique_key — dbt handles the MERGE.

Scheduling Patterns

Time-based

0 6 * * * — every day 6am UTC. Most common. Watch out for daylight savings.

Sensor-triggered

Wait for upstream signal — file arrives in S3, partition appears, API publishes.

Event-driven

Kafka message / S3 event triggers the run. Near-real-time.

Manual

Backfills, ad-hoc reruns. Always have a button.

Alerts & SLAs

  • Failure alert — task failed after all retries. Page on-call.
  • SLA miss — task didn't finish in time. Soft alert.
  • Freshness check — downstream-aware: "did dim_accounts update today?" dbt's source freshness tests this.
  • Route alerts to Slack channel + PagerDuty for true critical.

Flashcards

Click
What makes a pipeline idempotent?
Running it N times with the same input parameters produces the same output. Requires MERGE/upsert semantics or "delete-then-insert" for the date partition — not bare INSERTs.
Click
When would you use a sensor over a cron schedule?
When the upstream data arrival time is unpredictable — e.g., a Salesforce dump that might land 5–60 min after midnight. Sensor polls, fires when ready.
Orchestration Check
Your DAG failed mid-run yesterday. You re-trigger it today. The output table has duplicated rows. What's the root cause?
Recap
  • DAG = tasks + deps. Orchestrator handles schedule, retries, alerts, SLAs.
  • Idempotency is non-negotiable: MERGE or delete-then-insert.
  • Airflow is the industry default; Dagster gaining traction with asset-first model.
  • Sensors for unpredictable upstream; cron for fixed-time.

Ingestion & CDC

How data gets into the warehouse — and why CDC is the silent killer of analyst metrics.

"How does the data get here?" Batch dumps, ELT tools, Kafka streams — each has trade-offs. CDC (Change Data Capture) is the AE-critical pattern: streaming row-level changes from prod databases into the lake.

Ingestion Patterns

PatternHow it worksLatencyUse case
Batch ETLDaily SELECT * FROM prod → warehouse24hSmall dims, historical data
Incremental batchSELECT * WHERE updated_at > last_run1h-24hMost cases
CDC streamingRead DB binlog, stream changessecondsNear-real-time, high-volume
Event streamsApps write events to Kafka, consumed by stream → lakesecondsBehavioral data, telemetry
Managed ELTFivetran/Airbyte/Stitch handles it15min-24hSaaS sources (Salesforce, Stripe)

CDC Deep Dive

CDC reads the database's transaction log (MySQL binlog, Postgres WAL, MongoDB oplog) and emits one event per row change: insert, update, delete.

Typical CDC stack

Prod DB (MySQL) → Debezium → Kafka → Spark Streaming → Delta Lake (Bronze) → dbt (Silver) → Marts (Gold).

The CDC payload shape

{
  "op": "u",                       # c=create, u=update, d=delete, r=read (snapshot)
  "ts_ms": 1716000000000,
  "before": { "id": 1, "status": "active" },
  "after":  { "id": 1, "status": "closed" },
  "source": { "db": "prod", "table": "accounts" }
}

The CDC Reality

Critical knowledge — memorise

Raw kafka_cdc tables have __is_deleted column. Missing this filter = production bug. Required on:

job_assignments, accounts, sites, contacts, activation_keys, account_movements, subscriptions, ad_campaigns, site_abns, site_galleries, license_details

Always: WHERE __is_deleted = false (or = 0 for raw kafka).

Also: rows with active = 0 on these tables are in-place updates, not separate insert rows. Confirm mechanics before writing dedup logic.

Soft Delete vs Hard Delete

  • Soft delete: UPDATE accounts SET is_deleted=true. Row still in table.
  • Hard delete: DELETE FROM accounts. Row gone — only CDC op=d events remember it existed.
  • CDC pipelines must apply tombstone logic for hard deletes — usually flag __is_deleted = true in the silver layer and let downstream filter.

Kafka 101

ConceptMeaning
TopicNamed log of messages (e.g. prod.accounts.cdc)
PartitionTopic split for parallelism. Ordering is per-partition.
OffsetPosition of a message in a partition. Consumers track their offset.
ProducerWrites messages (Debezium, app code)
ConsumerReads messages (Spark Streaming, downstream apps)
Consumer GroupCoordinated set of consumers; partition assigned to one consumer in group
RetentionHow long messages stick around (e.g. 7 days)

Building a CDC Silver Model

-- silver layer: latest non-deleted row per account_id
with ranked as (
  select *,
    row_number() over (
      partition by account_id
      order by __op_ts desc
    ) as rn
  from bronze.kafka_cdc_accounts
)
select *
from ranked
where rn = 1
  and __is_deleted = false;

Schema Evolution

Source DB adds a column → CDC payload changes shape → downstream models break. Strategies:

  • Schema Registry (Confluent) — central schema authority; producers/consumers validate.
  • Delta schema evolution: MERGE WITH SCHEMA EVOLUTION auto-adds new columns.
  • Contracts — explicit agreement upstream/downstream on field types & required fields.

Flashcards

Click
What's the difference between batch incremental ingestion and CDC streaming?
Batch incremental runs SELECTs at intervals (every hour, etc.) — misses deletes & hard-to-detect updates if no updated_at. CDC reads the DB's binlog/WAL and emits every change in near-real-time, including deletes.
Click
Why is __is_deleted critical on kafka_cdc tables?
Hard deletes in prod produce a CDC tombstone row with __is_deleted = true. The row stays in bronze for replayability. If you don't filter it out in silver/marts, you're counting deleted records — production correctness bug.
CDC Check
A stakeholder reports the "active contractors" count from your model is 12% higher than the Sales team's CRM. You query accounts directly. What's the FIRST thing to check?
Recap
  • Ingestion spectrum: batch ETL → incremental batch → CDC streaming → events.
  • CDC = DB transaction log → Kafka → bronze; preserves inserts, updates, deletes.
  • Always filter __is_deleted = false on CDC tables. Always.
  • Schema evolution: registry + Delta SCHEMA EVOLUTION + contracts.

Data Quality & Testing

Trust is built one assertion at a time.

A correct query running on bad data still gives a wrong answer. AE owns the assertions that protect the company from "the dashboard is wrong" Slack messages at 9pm.

The 6 Dimensions of Data Quality

Completeness

No missing rows or columns. "Yesterday's orders should have ~1k rows; today says 12."

Uniqueness

Primary keys are actually unique. No duplicate user_ids.

Validity

Values conform to format/type. Email looks like an email. Status ∈ allowed set.

Accuracy

Values are right. Revenue matches Stripe / Salesforce / Zuora.

Consistency

Same metric, same number across tools. SF vs Tableau vs dbt agree.

Timeliness

Data is fresh — yesterday's data is available by 8am.

Trade-Off Frameworks to Reach For

Latency vs Cost

Real-time = streaming + always-on compute = $$$. Hourly batch = cheap. Map each use case to its real latency SLO.

Schema-on-Read vs Write

Bronze tolerates messy raw; gold enforces schema. Push validation as far left as cheap.

Build vs Buy

Fivetran (~$$$) vs custom Python ingestion (eng time). For SaaS sources: buy. For internal volume: build.

Push vs Pull

Push = producers publish to a stream (eventual consistency, decoupled). Pull = consumer queries source (simple, can hammer prod).

Normalized vs Denormalized Serving

BI loves wide tables; ML wants long. Often both — gold has narrow facts + wide reporting models.

Centralized vs Decentralized

Central platform team vs Data Mesh (each domain owns its data product). Hybrid is reality.

Capacity Planning — the back-of-envelope sniff test

  • 1B rows × 100 bytes = 100 GB raw. Parquet compresses ~5–10× → 10–20 GB on disk.
  • Scan throughput on Photon ≈ 1–3 GB/sec/worker. 20 GB table on 10-worker cluster → ~1s scan with filters.
  • Kafka throughput per partition ≈ 10 MB/s. Need 100 MB/s? ~10+ partitions.
  • dbt run time scales with model count + warehouse size. Slim CI cuts this 10×.

System Design Interview Template

  1. Clarify — what's the latency SLO, volume, accuracy bar, who consumes?
  2. Pick architecture — batch / streaming / lakehouse / lambda? Justify.
  3. Sketch flow — sources → ingestion → storage → transform → serve.
  4. Schema — fact/dim, grain, key choice, SCDs.
  5. Operational — orchestration, monitoring, alerts, DQ tests, contracts.
  6. Trade-offs — what did you simplify? What would v2 look like at 10× scale?

Worked Example: "Real-time contractor response-time dashboard"

Brief
Show contractors how their median lead-response-time compares to peers, refreshed within 5 minutes of every action.
  • Sources: lead-issued event, contractor-response event. Both already on Kafka.
  • Ingestion: Spark Structured Streaming reads both topics → write to bronze.
    5-min trigger, exactly-once via Delta + idempotent Kafka offsets.
  • Storage: bronze raw events; silver enriched with contractor + category dims (joined at stream-time); gold = rolling 30-day response time agg per contractor + category.
  • Transform: dbt incremental on silver→gold every 5 min via Workflows.
  • Serve: DBSQL Serverless warehouse, AI/BI dashboard with auto-refresh; or push to Postgres via reverse ETL for in-product widget.
  • DQ: unique on (contractor_id, lead_id, event_ts); not_null on contractor_id; row count delta vs 1h ago must be within 30%.
  • Cost trade-off: streaming all the way is expensive — 5-min micro-batch with serverless gives 90% of value at 30% of cost.

Anti-Patterns to Avoid in Design

  • Premature streaming — daily batch is enough; streaming adds 10× complexity.
  • One big table — denormalised "kitchen sink" looks easy; impossible to evolve.
  • No clear ownership — model has no owner = stale + wrong within 6 months.
  • Missing contracts — source team changes column, your model breaks at 3am.
  • Untested upserts — MERGE logic that introduces duplicates on edge cases.
Design Check
Stakeholder asks for "near-real-time" revenue dashboard. They concede 5-minute latency is fine. Which design wins on cost vs complexity?
Recap
  • Lakehouse = source → ingestion → bronze/silver/gold → serving + governance.
  • Always state SLOs (latency, freshness, accuracy) before picking architecture.
  • Streaming costs 10× more than batch — match latency to actual need.
  • Capacity planning: GB/s scan, MB/s Kafka partitions, dbt model count × size.
  • Anti-patterns: premature streaming, kitchen-sink tables, no ownership, no contracts.

SQL Practice — the 20 patterns to drill

  1. Find the second-highest salary per department.
  2. Running total per customer.
  3. Cumulative count of distinct users by day.
  4. Sessionization: group events into sessions when gap > 30 min.
  5. Top N per group.
  6. Dedup keeping latest by timestamp.
  7. Find customers who placed orders in two consecutive months.
  8. Active users yesterday but not today.
  9. Rolling 7-day moving average.
  10. Percent of total per group.
  11. Median per group (without MEDIAN function).
  12. Funnel: conversion at each step.
  13. Retention cohort: signup_month vs active_month.
  14. Gaps and islands: consecutive date ranges.
  15. Self-join: manager/employee hierarchy.
  16. Pivot fact data by category.
  17. Anti-join: customers with no order.
  18. Detect duplicates and quantify them.
  19. Reconciliation: SUM(a) per id vs SUM(b) per id, find mismatches.
  20. Window with frame: 30-day rolling SUM via ROWS BETWEEN INTERVAL ….
