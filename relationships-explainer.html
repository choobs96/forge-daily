Relationships Tests in Multi-Layer Lineage

How dbt's relationships test actually behaves when data flows A → B → C — visually.

1 The test is one-hop, not a chain walker

A relationships test on a column compares exactly two tables: the model it's declared on (child) and the to: target (parent). It does not traverse lineage.

Valid FK (exists in parent)
Orphan (no matching parent)
Test would FAIL
A999 in fct_jobs.account_id has no matching row in dim_account.account_id. The test returns 1 orphan row → severity error blocks the build.

The reverse situation — A004 exists in the parent but no child references it — does NOT fail. Unused dim rows are fine.

2 A → B → C: where do you put the test?

When the same column flows through 3 layers (staging → intermediate → marts), you don't test every hop. Pick the layer that matters.

Why only the terminal layer?

The column is the same value at every layer (passthrough). If the test would pass on C, it would also pass on A and B. Testing all three is redundant work for the warehouse.

The rule
Test relationships at the layer where stakeholders consume — typically marts. Earlier layers covered transitively.

3 When transitivity breaks: filters in the chain

If a middle layer filters out rows, you can't rely on testing only the terminal layer. Click between scenarios:

Transitive guarantee holds
invoice → quote passes and quote → lead passes, so every invoice transitively has a valid lead. You don't need a third test invoice → lead.
Transitivity broken
dim_active_quote dropped 3,000 inactive quotes. Invoices referencing those quotes are now orphans relative to the filtered dim, even though they're valid relative to the upstream unfiltered table. The test failure is real — it surfaces a business question: "why do we have invoices for inactive quotes?"
Decision time
Either fix data ("invoices shouldn't reference inactive quotes"), or relax the test (severity: warn + investigate periodically), or change the FK target (dim_invoice → dim_lead directly, skipping the filtered layer).

5 Five facts, one dim — fan-out pattern

When 5 different fact tables all have account_id referencing dim_account, each declares its own test. dbt runs 5 separate queries.

Three ways to keep it DRY

1. YAML anchors

Define once in a single file, reference 5× via *anchor. Works within one yml.

# in one file only
x-account-fk: &account-fk
  - relationships:
      to: ref('dim_account')
      field: account_id

models:
  - name: fct_jobs
    columns:
      - name: account_id
        tests: *account-fk

2. Custom generic test

Write a test macro once, call it by name 50×.

-- tests/generic/fk_to_dim_account.sql
{% test fk_to_dim_account(model, column_name) %}
  select count(*) from {{ model }} c
  left join {{ ref('dim_account') }} p
    on c.{{ column_name }} = p.account_id
  where c.{{ column_name }} is not null
    and p.account_id is null
{% endtest %}
Performance reality
5 tests = 5 aggregation queries. On a serverless DBSQL warehouse with parallel test execution, this is seconds, not minutes. Slim CI (dbt build -s state:modified+) only runs tests on changed models — even cheaper.

6 Pattern 1: meta: — structured documentation

meta: is a free-form key-value block on any dbt resource. It's pure documentation — never validated, never run as SQL — but it's machine-readable, which is what makes it useful.

What it looks like

# declare the FK intent — no test, no enforcement
- name: fct_opportunities
  columns:
    - name: account_id
      description: "Salesforce 18-char Account ID. Joins to dim_accounts.id."
      meta:
        join_to: "dim_accounts.id"
        fk_strict: false      # your own convention — orphans tolerated
        owner: "sales-analytics"
        pii: false

How it flows through dbt's pipeline

What you get — 4 concrete benefits

1. Lineage for tools that can read it

Atlan, DataHub, dbt Cloud Explorer parse meta and draw FK lines between models on lineage diagrams. dbt's own DAG won't, but third-party catalogs will.

2. Better AI-generated SQL

Genie, Cursor, and any LLM-driven query writer get a structured signal that "account_id on this model joins to dim_accounts.id." Free-text descriptions don't parse reliably.

3. Programmatic audits

Write a Python script that walks manifest.json and lists every declared FK, every PII column, every owner. Impossible with prose descriptions.

4. Future-proof

Once meta is in place, a future PR can read all join_to: declarations and auto-generate relationships tests. The data is structured; tests become a downstream artifact.

When to reach for meta
  • You want to document an FK without enforcing it (orphans tolerated)
  • You want lineage to surface in external catalog tools
  • You need conventions for ownership, PII flags, freshness expectations
  • You're laying groundwork for future automation/tests
Cost
Free to add. Zero runtime cost. The only "cost" is convention discipline — meta keys are free-form, so the team needs to agree on naming (join_to vs references vs fk) and document it in AGENTS.md or it drifts.

7 Pattern 2: relationships — drift detection

relationships is a generic test that runs at build time. It's not documentation — it's an assertion that fires an alert when reality drifts from intent.

The three configurations you'll actually use

Basic — strict FK enforcement

- name: account_id
  tests:
    - relationships:
        to: ref('dim_accounts')
        field: id

Fails the build on any orphan. Use only when you're confident the FK truly holds.

Pragmatic — warn instead of block

- name: account_id
  tests:
    - relationships:
        to: ref('dim_accounts')
        field: id
        config:
          severity: warn

Logs orphans without blocking. Surfaces in run_results.json, Elementary, Slack. Ideal entry-point for adding relationships to a legacy codebase.

Surgical — known-orphan filter

- name: account_id
  tests:
    - relationships:
        to: ref('dim_accounts')
        field: id
        config:
          severity: warn
          where: "account_id != '0010000000000000AAA'"
          error_if: ">100"
          warn_if: ">0"

Excludes a known sentinel ('Unknown Account' MD5 = cfcd2084…), warns above 0 orphans, fails only if it explodes past 100. The compromise the dbt project should have made instead of disabling the test entirely.

What happens at dbt build time

What you get — 4 concrete benefits

1. Catches regressions automatically

The moment orphan rate goes from 0.1% to 5% (upstream bug, broken filter, schema change), the build alerts. Meta would stay silent forever.

2. Defines a measurable SLA

"Less than 100 orphans" is an explicit, testable contract. Stakeholders can ask "is the FK clean?" and get a deterministic answer.

3. Blocks bad data from spreading

With severity error, downstream models don't get built if the FK is broken. Stops a bad metric reaching Tableau before anyone sees it.

4. Generates evidence for incidents

Failed test results land in run_results.json, Elementary, or your alerting tool — searchable history of when drift started.

Cost
One aggregation SQL query per declared test, per build. Cheap individually, adds up at scale. Mitigate with slim CI (state:modified+), tags, and severity: warn on non-critical FKs.

8 The layered approach — use both together

meta and relationships aren't substitutes. Each answers a different question. The mature pattern is to declare intent in meta on every FK, and add a relationships test where drift is worth monitoring.

Side-by-side comparison

Question meta.join_to relationships test
What does it answer?"This is intended to join here""Does the join actually hold?"
When does it run?Never — pure metadataEvery dbt build / dbt test
CostZero runtime cost1 SQL query per declaration
Catches drift?NoYes (the whole point)
External catalogs see it?Yes (Atlan, DataHub render FK lineage)Partially (results, not the declaration)
AI tools see it?Yes — structured = LLM-friendlyIndirectly
Blocks bad builds?NoYes (with severity: error)
Good when data is messy?Yes — document without enforcingUse severity: warn to soften

The recommended pattern in full

version: 2
models:
  - name: fct_opportunities
    description: "Salesforce opportunities. Grain: one row per opportunity_id."
    meta:
      owner: "sales-analytics"
      grain: "opportunity_id"
    columns:
      - name: opportunity_id
        description: "Primary key — Salesforce 18-char ID"
        tests:
          - unique
          - not_null

      - name: account_id
        description: "FK to dim_accounts.id (Salesforce Account.Id)"
        meta:                                  # intent → structured, machine-readable
          join_to: "dim_accounts.id"
          fk_strict: false
        tests:                                 # reality → drift detection
          - not_null
          - relationships:
              to: ref('dim_accounts')
              field: id
              config:
                severity: warn           # start gentle, harden later

How they reinforce each other

Decision flow — what to add when

The practical recommendation

For a dbt project where 0 FKs are currently documented or tested:

  1. Week 1: Add meta.join_to to every FK column across marts. Zero risk, zero cost, pure documentation upgrade.
  2. Week 2: Pick 3 marts with cleanest data (e.g. fct_opportunities, dim_accounts downstream). Add relationships tests with severity: warn.
  3. Week 3+: Monitor warn-only test results. Where orphan rate is <0.1%, harden to severity: error. Where it's higher, investigate root cause (CDC timing, soft-delete asymmetry, missing dim rows).
  4. Add to AGENTS.md: "All FK columns must declare meta.join_to. relationships tests on FKs are encouraged with severity: warn at minimum."

9 Quick scenarios — does the test pass?

Click each scenario to reveal the verdict.

Scenario A

fact has rows with account_id = A001, A002. dim has A001, A002, A003.

PASS — every child FK exists in parent; extras in parent are fine

Scenario B

fact has A001, A002, A999. dim has A001, A002.

FAIL — A999 in child has no match in parent (orphan)

Scenario C

fact has A001, A002, NULL. dim has A001, A002.

PASS — NULLs are ignored by relationships test (only checks non-null values)

Scenario D

Both fact and dim are empty.

PASS — no orphans because no rows. Trivially true.

Scenario E

fact has 1M rows including 12 with deleted account_ids. dim filters __is_deleted = false.

FAIL — soft-delete asymmetry. Classic CDC pattern. Fix: severity: warn or filter the fact too.

Scenario F

fact and dim have same data, but loaded at different times. CDC for fact lands at 10:00, for dim at 10:05. Build runs at 10:02.

FAIL TEMPORARILY — 3-min orphan window. Fix: order ingestion in the DAG, or add latency buffer to incremental filter.

10 Summary cheat sheet

FK contract layer guide

Situation meta? relationships test?
Brand new FK, data quality unknownYesYes, severity: warn
Clean, mature FK on a martYesYes, severity: error
FK with known orphan patternYes (+ fk_strict: false)Yes, where: ... + warn
Internal column, not a true FKNoNo
Staging passthrough, FK is on the martNo (declare on mart)No (test on mart)
5 facts share same FKYes, on each (or via project-level)Yes — use YAML anchor or generic test macro

Test-placement guide (chain depth)

Situation Where to place
Column passes through stg → int → mart unchangedMart layer only
Intermediate joins introduce new FK columnIntermediate and mart layer
Middle layer filters rows (WHERE active)Every hop where filter applies
Soft-delete asymmetry (CDC pattern)severity: warn + where: __is_deleted = false
If you remember three things
  1. meta = intent, test = reality. Use both; they answer different questions.
  2. The test is one-hop. Place where orphans matter (mart) + any layer where joins/filters could introduce drift.
  3. Start with severity: warn. Harden to error as the FK proves itself clean. Never disable — that's the anti-pattern.
